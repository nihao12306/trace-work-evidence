# ADR-010：外部数据来源采用本地伴侣，不部署 OAuth 后端

日期：2026-08-12  
状态：已确认，分阶段实现

## 背景

Trace 需要逐步接入飞书和用户主动选择的 Codex 工作记录，帮助用户减少重复记录。但 Trace 的核心承诺仍是本地优先、证据可追溯和外部读取默认关闭。把飞书应用密钥或长期 Token 放进公开的 Vite 前端不可接受；部署集中式 OAuth 后端又会让用户资料经过项目作者维护的服务器，并扩大安全与隐私责任。

## 决策

第一版不部署集中式 OAuth 后端。外部来源采用可选的最小本地伴侣程序：

- 伴侣运行在用户自己的电脑上；
- Trace 浏览器页面只通过版本化 localhost 协议发起明确请求；
- 伴侣默认只读，只处理用户选择的来源和范围；
- 导入先返回预览，用户确认后才写入 Trace 的本地材料层；
- 伴侣不负责 AI 总结、证据判断或周报生成；
- 伴侣未运行时，手动记录、文件导入和核心证据闭环必须可用；
- 第一版不做全量扫描、后台持续同步或跨设备同步。

## 被放弃的选项

### 集中式 OAuth 后端

优点是免安装、在线体验统一；代价是需要服务器、Token 保护、隐私政策、数据删除和持续维护。它也会改变 Trace 的“数据默认留在本地”认知，不作为第一版方案。

### 纯浏览器直接连接飞书

公开前端无法安全保存应用密钥；即使完成授权，也容易把读取范围和 Token 处理隐藏在用户看不见的代码里。纯浏览器方案只保留手动/文件导入，不承担真实飞书连接。

### 扫描整个 Codex 历史目录

Codex 内部存储可能包含敏感信息，格式也不是 Trace 可以依赖的稳定公共接口。第一版只允许用户主动选择任务或导出内容。

## 后果

- 用户需要额外运行一个小程序，安装成本高于纯网页方案；
- Trace 必须把“连接、授权、范围选择、预览、确认导入”拆成可理解的步骤；
- 需要维护本地伴侣协议版本和失败状态；
- 在真实在线飞书授权完成前，本地目录读取适配器可以先独立工作；健康检查和范围预览仍然不等于在线账号授权；
- 如果未来转向集中式 OAuth、官方 API 或后台同步，必须重新评估隐私边界并新增 ADR，不得通过普通功能提交默默改变架构。Codex/飞书本地读取器的具体范围见 ADR-018。
