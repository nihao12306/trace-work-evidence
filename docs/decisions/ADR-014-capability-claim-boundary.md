# ADR-014：能力主张的单项目边界

状态：已采用

日期：2026-08-13

## 背景

Trace 保存证据的长期意义，不是累计“做过多少事”，而是让用户在需要周报、复盘、述职或作品集时，能够从一段完整工作经历中说明：当时处在什么情境，做了什么判断和行动，产生了什么结果，以及这段经历支持怎样的能力表达。

如果系统把一条记录直接改写成“能力”，很容易把一次偶然的成功夸大成稳定特质，也会让用户误以为能力主张等同于自动生成的简历标签。因此，能力必须建立在已经整理过、确认过、并且完成定稿的项目案例之上。

## 决策

1. 能力主张只能由用户从一份已定稿的项目案例主动创建。案例定稿不会自动创建或确认能力主张。
2. 新建内容先保存为“能力线索”（`reviewState=draft`）。它可以只有情境和行为证据，用来保留一个值得继续观察的方向，但不能被当作已确认能力。
3. 用户确认前，页面必须同时展示并校验：
   - 情境与约束；
   - 至少一条行动或决策证据；
   - 至少一条结果或反馈证据；
   - 来源项目案例已经定稿；
   - 单项目的证据范围和限制说明。
4. 第一版能力主张固定为 `scope=single_project`。它只能表达“在这段项目案例中有证据支持”，禁止写成“长期稳定”“持续擅长”“始终能够”等跨项目结论。
5. 能力主张保留证据 ID 和案例 ID，不复制或覆盖原始记录；拒绝、修改和确认都保留在同一条主张的审核状态中。
6. 第一版不提供能力评分、等级、岗位匹配、简历生成或跨项目聚合。未来若要增加跨项目能力，必须先有多个独立定稿案例，并另行讨论范围、迁移和导出语义。

## 结果

- 用户可以把“我可能形成了什么能力”作为一个可继续补证的线索保存下来。
- 已确认能力主张能回到案例和证据，且不会把一次项目经验伪装成长期稳定能力。
- 能力页面是证据的表达层，不是新的任务系统或评分看板。

## 被放弃的替代方案

- 案例定稿后自动生成并确认能力：会绕过用户判断，也无法处理结果不足的情况。
- 只保存一段能力文字、不保存证据 ID：无法回溯，违背证据优先原则。
- 直接建立全局能力标签库：会在第一版引入评分、聚合和简历化表达，超出当前核心闭环。
